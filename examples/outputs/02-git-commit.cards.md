# 知识卡片：如何写好的 Git commit message

（输入类型：操作流程 / 建议清单 · 6 张卡片）

### 卡片 1：commit message 的目的是说明"为什么"
- **核心知识**：commit message 的作用是告诉未来的读者这次改动为什么发生，因此应说明"为什么"，而不只是"做了什么"。
- **简明解释**：代码的 diff 已经显示了"做了什么"，message 应当补充 diff 无法表达的动机和背景。
- **例子 / 自测**：自测——既然 diff 已经展示了改动内容，commit message 还应补充什么？

### 卡片 2：约定式提交的格式
- **核心知识**：推荐使用约定式提交格式 `类型(范围): 描述`。
- **简明解释**：常见类型包括 feat（新功能）、fix（修复 bug）、docs（文档）、refactor（重构）、test（测试）、chore（杂项）。
- **例子 / 自测**：例子——`feat(login): 支持手机号验证码登录`。

### 卡片 3：标题行的两条要求
- **核心知识**：标题行应控制在 50 个字符以内，并使用祈使语气。
- **简明解释**：动词用祈使式，比如写 "add retry logic" 而不是 "added retry logic"。这样能与 Git 自动生成的 Merge... / Revert... 保持一致。
- **例子 / 自测**：自测——标题行建议的字数上限是多少？应当用什么语气？

### 卡片 4：正文的排版规范
- **核心知识**：标题下空一行后再写正文，正文每行不超过 72 个字符。
- **简明解释**：复杂改动应在正文中分段解释背景和取舍；限制行宽是为了方便在终端里阅读。
- **例子 / 自测**：自测——正文建议的每行字符上限是多少？

### 卡片 5：一个 commit 只做一件事
- **核心知识**：一个 commit 应当只做一件事，出现"并且""顺便"通常意味着应该拆分。
- **简明解释**：这样做的意义是：一旦出问题，可以精确地回滚单个改动，而不必牵动无关的代码。
- **例子 / 自测**：自测——把一次改动拆成多个 commit，最大好处是什么？

### 卡片 6：避免模糊描述
- **核心知识**：不要写"修复了一些 bug"这类模糊描述，模糊的 message 等于没有 message。
- **简明解释**：模糊描述无法传递 diff 之外的任何信息，对未来的读者没有价值。
- **例子 / 自测**：自测——"修复了一些 bug"为什么是一个不合格的 commit message？
