# 知识卡片：什么是 REST API

（输入类型：技术概念文章 · 6 张卡片）

### 卡片 1：REST 是什么
- **核心知识**：REST（表述性状态转移）是一种用于设计网络接口的架构风格，由 Roy Fielding 在 2000 年的博士论文中提出。
- **简明解释**：它把服务器上的每样东西都看作一种"资源"，并用统一的 URL 来标识资源。它不是一套强制标准，而是一种设计风格。
- **例子 / 自测**：自测——REST 的全称是什么，它属于标准还是风格？

### 卡片 2：HTTP 方法在 REST 中的语义
- **核心知识**：REST 用 HTTP 方法本身表达对资源的操作：GET 读取、POST 创建、PUT 整体替换、PATCH 部分更新、DELETE 删除。
- **简明解释**：方法带有明确的语义，因此操作类型应当由方法承载，而不是写进 URL。
- **例子 / 自测**：自测——要"部分更新"一个资源，应该用哪个 HTTP 方法？

### 卡片 3：无状态
- **核心知识**：REST 要求无状态，即服务器不保存两次请求之间的客户端状态，每个请求都必须自带完成它所需的全部信息。
- **简明解释**：因为任意一台服务器都能独立处理任意一个请求，无状态让服务器更容易横向扩展。
- **例子 / 自测**：自测——无状态给系统扩展性带来了什么好处？

### 卡片 4：面向资源而非面向动作
- **核心知识**：REST 的接口应围绕资源（名词）组织，动作交给 HTTP 方法，而不是把动作塞进 URL。
- **简明解释**：删除 ID 为 5 的用户，好的设计是 `DELETE /users/5`，而不是 `GET /deleteUser?id=5`。后者把动作编码进了 URL，违背了面向资源的原则。
- **例子 / 自测**：例子——`DELETE /users/5` 优于 `GET /deleteUser?id=5`。

### 卡片 5：REST 是风格，严格的 REST 还要求 HATEOAS
- **核心知识**：REST 是风格而非强制标准，很多号称 REST 的接口只做到了部分原则；严格的 REST 还要求 HATEOAS。
- **简明解释**：HATEOAS 指响应中携带指向后续可用操作的链接，但这一点在实践中很少被实现。
- **例子 / 自测**：自测——HATEOAS 要求响应中额外包含什么？现实中它被普遍实现了吗？

### 卡片 6：REST 与 RPC 的关注点差异
- **核心知识**：RPC 关注"调用某个函数"，REST 关注"对某个资源做什么操作"。
- **简明解释**：这一差异正是 REST 接口通常围绕名词（资源）来组织 URL、而 RPC 接口更强调动作的原因。
- **例子 / 自测**：自测——为什么 REST 接口的 URL 多以名词为主？
