# make-knowledge-cards

一个开源 Skill：把一篇文章（粘贴的文本，或本地的 `.md` / `.txt` 文件）提炼成 **5~8 张知识卡片**。

## 1. 项目解决什么问题

读了一篇长文，过几天只记得"好像讲过点什么"，却想不起关键结论——这是很常见的困境。根因通常是：**原文信息密度低、结构差，而且需要自己动手才能提炼出可复习的要点**。

人工做这件事有三个痛点：

- **不知道该留什么** —— 文章里往往夹杂大量背景、铺垫、轶事、套话，真正有价值的知识点只占一小部分。
- **容易写成摘要而不是知识点** —— 摘要是"文章讲了什么"，知识卡片应该是"记住了什么"，两者不是一回事。
- **容易顺手"脑补"** —— 整理时很容易加入原文没写、但自己知道的内容，结果卡片不再忠实于原文。

本项目把"提炼知识卡片"固化成一套可复用的流程和规则，让结果满足三点：**只留真正重要的知识、一张卡片只讲一个知识点、绝不编造原文没有的信息**。同时明确：**原文信息不足时不强行凑数**，宁可只输出 3 张卡片。

## 2. 主要功能

- **两种输入**：粘贴的文本；本地 `.md` / `.markdown` / `.txt` 文件。
- **输出 5~8 张知识卡片**，每张包含四个字段：
  | 字段      | 说明                                |
  | ------- | --------------------------------- |
  | 标题      | 这个知识点的名字（短语，不是句子，不含"第一点"之类序号）     |
  | 核心知识    | 一句话说清要记住的内容                       |
  | 简明解释    | 2~4 句，讲清它是什么、为什么、怎么用              |
  | 例子 / 自测 | 原文有具体例子时原样保留；否则给出一个能用本卡片内容回答的自测问题 |
- **按题材自适应取点**：技术概念取定义与机制，操作类文章取可独立执行的要点，观点议论取中心论点与其独立论据，科普解释沿因果链取点。
- **质量约束内置**：去重合并、不编造、保留原文限定词与精确数字（如 `50 字符`、`1/λ⁴`）、卡片按"从基础到派生"排序。
- **语言跟随原文**，并保留原文术语（如 `feat`、`GET` 不强行翻译）。

**不支持的场景**（不做隐性尝试，会明确说明并给出替代路径）：

- ❌ 网页抓取 / URL
- ❌ PDF、Word、PPT、图片等二进制文档
- ❌ Anki（`.apkg`）等记忆软件导出
- ❌ 图形界面

## 3. 安装方法

本 Skill 是纯目录形式，**没有第三方依赖，也不需要安装脚本**，把它放到 Skill 目录即可。

**方式一：作为项目级 Skill（跟随本仓库）**

仓库结构即最终形态，克隆/复制到本地后，`skills/make-knowledge-cards/` 就在项目内可直接使用：

```bash
git clone <your-repo-url> first_skill
cd first_skill
```

**方式二：安装为个人级 Skill（所有项目可用）**

把 Skill 目录复制到用户级 Skill 目录：

```bash
# Windows (Git Bash)
cp -r skills/make-knowledge-cards "C:/Users/<你的用户名>/.workbuddy/skills/"

# macOS / Linux
cp -r skills/make-knowledge-cards ~/.workbuddy/skills/
```

**校验安装是否正常**（可选，需要 Python 3）：

```bash
python quick_validate.py skills/make-knowledge-cards
# 期望输出：Skill is valid!
```

> `quick_validate.py` 是 Skill 创作工具链自带的官方校验脚本，用于检查 frontmatter 与命名规范。

## 4. 使用方法

**第一步：准备输入** —— 把文章粘贴到对话里，或给出一个本地文件路径。

**第二步：用自然语言触发** —— 以下任意说法都会激活该 Skill：

- 把这些内容做成知识卡片
- 帮我提炼成卡片
- 生成知识卡片
- make knowledge cards from this

**第三步：查看输出** —— Skill 按固定流程执行：

```
读取原文 → 提取候选知识点 → 去重合并 → 决定卡片数量 → 按字段写卡片 → 输出 Markdown 卡片列表
```

输出形如：

```
### 卡片 N：<标题>
- **核心知识**：<一句话>
- **简明解释**：<2-4 句>
- **例子 / 自测**：<具体例子，或一个自测问题>
```

**行为约定：**

- 卡片数落在 5~8 区间，或丢弃了较多材料时，会在卡片前加一行简短说明；否则直接输出卡片。
- 传入多个文件时会一次处理一个，如需合并请明确说明。
- 文件路径不存在、扩展名不支持时，会直接说明并停止，不会猜测解析方式。

## 5. 输入输出示例

### 示例一：科普文章

**输入**（`examples/inputs/04-why-sky-blue.md`，节选）：

> 大气中的氮气、氧气等分子尺寸远小于光的波长，短波长的光（蓝、紫）比长波长的光（红、橙）更容易被这些分子散射，这种现象称为瑞利散射，它的强度与波长的四次方成反比。因此蓝光被大量散射到四面八方，使天空整体呈现蓝色。

**输出**（节选，完整 5 张见 `examples/outputs/04-why-sky-blue.cards.md`）：

```
### 卡片 1：瑞利散射
- **核心知识**：大气中的氮气、氧气分子尺寸远小于光的波长，使短波长的光（蓝、紫）比长波长的光（红、橙）更容易被散射，这种现象称为瑞利散射。
- **简明解释**：瑞利散射的强度与波长的四次方成反比——波长越短，散射越强。
- **例子 / 自测**：自测——瑞利散射的强度与波长的几次方成反比？

### 卡片 2：天空为什么呈蓝色
- **核心知识**：蓝光被大气大量散射到四面八方并进入眼睛，使天空整体呈现蓝色。
- **简明解释**：太阳光本是各种颜色光的混合，因为蓝光散射最强，我们从各个方向看到的散射光便以蓝色为主。
- **例子 / 自测**：自测——我们看到的是直射的阳光，还是被散射到各处的阳光？
```

### 示例二：信息不足的短文（不凑数）

**输入**（`examples/inputs/05-thin-source.txt`，全文）：

> 据研究，每天喝够八杯水有助于维持身体的正常代谢。人体大约有 60% 是由水构成的。缺水会明显影响体能和注意力。因此建议大家随身带水，在感到口渴之前就补充水分。

**输出**（`examples/outputs/05-thin-source.cards.md`，节选）：

```
# 知识卡片：关于饮水的短文

（输入类型：信息量不足的短文 · 仅 3 张卡片）

> 说明：原文只有几句话，能提炼出的独立知识点不足 5 个，因此不凑数，只输出 3 张卡片。

### 卡片 1：人体含水比例
- **核心知识**：人体大约有 60% 是由水构成的。
- **简明解释**：水占人体比重很高，这也解释了为什么水对维持身体机能如此关键。
- **例子 / 自测**：自测——人体大约有多少比例是由水构成的？
```

## 质量规则

以下规则已内置在 `SKILL.md` 中，是输出质量的判断标准：

| 规则        | 说明                              |
| --------- | ------------------------------- |
| 只留真正重要的知识 | 定义、机制、因果、规则、关键区分优先；删除轶事、套话、重复表述 |
| 一张卡片一个知识点 | 若核心内容需要"并且"连接两个独立想法，就拆成两张       |
| 去重合并      | 用"能否用同一道自测题回答"判断该合并还是该拆分        |
| 不编造       | 内容必须能在原文找到依据；原文没说的（哪怕是常识）一律不写   |
| 不强行凑数     | 可提炼的独立知识点不足 5 个时，输出少于 5 张并说明原因  |
| 保持忠实      | 保留原文的数字、术语与限定词（如"通常在…"）         |
| 卡片记的是知识   | 不做文章结构、作者或叙事的摘要                 |
